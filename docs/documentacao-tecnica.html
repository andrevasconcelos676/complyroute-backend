1. Visão Geral

O ComplyRoute é um gateway de pagamento que atua como camada de orquestração entre o lojista/marketplace e múltiplos subadquirentes (Cielo, Rede, Stone, PagSeguro, GetNet, SafraPay, Zoop, Asaas, OrendaPay e Necta Multi-Pay). Ele decide, transação a transação, para qual subadquirente enviar o pagamento — por método, valor, parcelamento, país do cartão, score de risco e saúde operacional dos próprios subadquirentes — e expõe uma API única e estável para quem consome a plataforma, independente de qual gateway processou o pagamento por trás.

Capacidades principais:

  • Processamento de transações (crédito, débito, PIX, boleto) com roteamento automático;
  • Motor antifraude com score 0–100 baseado em sinais compostos;
  • Estorno (total) de transações aprovadas;
  • Conciliação financeira por subadquirente e período;
  • Webhooks de saída (eventos da plataforma para os sistemas do cliente) e de entrada (eventos recebidos de um subadquirente real — hoje, Necta Multi-Pay);
  • Dashboard web (/dashboard) para operação e monitoramento.

2.3 Middleware de autenticação global

Um middleware HTTP único (main.py) protege todas as rotas por padrão, exigindo Authorization: Bearer <jwt> válido. As exceções explícitas são:

  • Caminhos públicos fixos: /, /health, /docs, /redoc, /openapi.json, /metrics, /dashboard;
  • POST /api/v1/auth/login e POST /api/v1/auth/refresh;
  • POST /api/v1/acquirers/necta/webhook — autenticado por assinatura Svix, não por JWT (é a Necta chamando o ComplyRoute, não um usuário).
Qualquer novo endpoint público (chamado por um sistema externo, não por um usuário logado) precisa ser adicionado explicitamente a essa lista em main.py — do contrário recebe 401 antes mesmo de chegar no router.

3.2 Fluxo de login

MétodoRotaDescrição
POST/api/v1/auth/loginE-mail + senha. Se o usuário tiver 2FA ativo e totp_code não for enviado, retorna requires_2fa: true sem tokens.

3.3 Chaves de API

O modelo APIKey existe (prefixo sk_live_/sk_test_, hash SHA-256, escopos full/readonly/sandbox), e o dashboard tem um painel "API Keys" — mas não há endpoint de API para gerenciá-las hoje. É um recurso modelado no banco, ainda não exposto.

4. Motor de Roteamento

Implementado em app/services/routing_engine.py como uma lista fixa, no código de 12 regras avaliadas em ordem de prioridade — não é lida da tabela routing_rules no banco (essa tabela e o endpoint GET /api/v1/routing/rules hoje só espelham/listam, não alimentam o motor).

4.1 As 12 regras (em ordem de avaliação)

#RegraAção
1PIX → Rederoute
2Boleto → bloquear SafraPay (não suporta boleto)block_acquirer
3Débito → bloquear OrendaPay (não suporta débito)block_acquirer
4Crédito acima de R$ 10.000 → Cieloroute
5Boleto → Asaasroute
6PIX → Rede (redundante com a #1)route
7Débito → Cieloroute
8Parcelas ≥ 12x → Stoneroute
9BIN internacional → PagSeguro (desativada por padrão)route
10Score antifraude < 50 → bloquearblock
11Timeout no adquirente primário → GetNet (fallback)route
12Retry automático em timeout (até TXN_MAX_RETRIES)retry

A regra 10 (antifraude) é sempre avaliada primeiro, com prioridade máxima, antes de qualquer outra — inclusive antes do override manual descrito abaixo. Se nenhuma regra rotear a transação, o fallback padrão é DEFAULT_ACQUIRER = "cielo".

4.2 Override manual (metadata.force_acquirer)

Para validar integrações novas sem alterar o roteamento padrão de ninguém, uma transação pode enviar "metadata": {"force_acquirer": "necta"} e pular direto para aquele subadquirente. Duas restrições de segurança:

  • Avaliado depois do bloqueio antifraude — não serve para contornar o antifraude;
  • Só funciona quando APP_ENV != "production" — não é uma feature para o chamador da API escolher livremente o subadquirente em produção.

4.3 Simulação

POST /api/v1/routing/simulate avalia as regras sem criar uma transação — retorna o subadquirente selecionado e a trilha completa de decisão (cada regra avaliada, se casou e qual ação tomou). Útil para depurar por que uma transação foi (ou seria) roteada para determinado subadquirente.

5. Motor Antifraude

Implementado em app/services/fraud_engine.py. Score final = 100 − média ponderada das penalidades dos cinco sinais abaixo. Score < 50 bloqueia a transação.

SinalPesoStatus de implementação
Velocidade de IP30%Placeholder — sempre 0 (produção: janela deslizante no Redis)
Device fingerprint20%Penalidade leve (10) só quando ausente; sem checagem real de reuso
BIN em lista negra25%Placeholder — sempre 0 (produção: tabela de BINs bloqueados)
Divergência geográfica (país do cartão vs. IP)15%Placeholder — sempre 0 (produção: geolocalização de IP)
Valor anômalo para o método10%Implementado: PIX > R$20.000 e crédito à vista > R$30.000 penalizam
A maioria dos sinais são placeholders documentados no próprio código-fonte. O motor está com a arquitetura pronta (interface, pesos, composição), mas os sinais de maior peso (velocidade de IP, BIN) ainda não têm implementação real.

6. Transações

MétodoRotaDescrição
POST/api/v1/transactionsCria e processa uma transação: antifraude → roteamento → subadquirente → persistência.
GET/api/v1/transactionsLista com paginação e filtros (status, method, acquirer).

6.1 Ciclo de vida do status

pending → processing → approved | declined, e a partir de approved: refunded ou chargeback.

6.2 Envio ao subadquirente

Após o roteamento decidir o subadquirente, o endpoint consulta AcquirerClientFactory.get(nome):

  • Se existir um cliente real configurado (hoje, apenas "necta", e só quando NECTA_CLIENT_SECRET/NECTA_SECRET_KEY estão definidos) → chama a API real do gateway;
  • Caso contrário (todos os demais subadquirentes hoje) → resposta simulada (approved, código de autorização e NSU gerados localmente). Isso é intencional e pré-existe à integração Necta: nenhum outro subadquirente tem cliente HTTP real implementado ainda.

Uma falha do cliente real (AcquirerError) persiste a tentativa como declined com o motivo do erro e propaga 502/504 ao chamador.

8. Integração — Necta Multi-Pay

Única integração com um subadquirente real hoje. Cliente em app/services/acquirers/necta.py, contra a API pública documentada em doc.nectaco.com.br (OpenAPI 3.1, servida em /openapi/v1).

8.1 Autenticação

Máquina-a-máquina: POST /auth com {clientSecret, secretKey} (gerados em POST /api-tokens no painel Necta) retorna um JWT usado em Authorization: Bearer. O NectaClient cacheia o token por 25 minutos e reautentica automaticamente uma vez em caso de 401.

8.2 Criação de venda (um passo por método)

Método internoEndpoint Necta
pixPOST /sales/pix
creditPOST /sales/credit-card
boletoPOST /sales/bank-slip
debitNão suportado — lança AcquirerError

O comprador (buyer) exige nome, documento, e-mail, telefone e endereço completo. Como o schema CustomerData do ComplyRoute só exigia nome/documento/e-mail, foram adicionados campos opcionais phone_number e address. Quando ausentes, o cliente registra um aviso e envia um endereço placeholder — aceitável para teste, não recomendado para tráfego real (ver seção 15).

8.3 Mapeamento de status

Status NectaStatus ComplyRoute
pending, processing, scheduled, pre_authorizedprocessing
paidapproved
refunded, partially_refundedrefunded
canceled, denied, refused, expireddeclined

8.4 Estorno

POST /sales/{uuid}/void — sem corpo é estorno total; com {"amount": N} seria parcial (Necta só suporta parcial em alguns gateways; o ComplyRoute hoje só envia estorno total pelo endpoint /transactions/{id}/refund).

8.5 Webhook de entrada

POST /api/v1/acquirers/necta/webhook recebe sale.paid, sale.refunded e sale.failed da Necta e atualiza a transação correspondente (localizada por acquirer_txn_id). Isento do middleware de JWT (seção 2.3) — autenticado por assinatura no padrão Svix:

svix-id: msg_...
svix-timestamp: <unix ts>
svix-signature: v1,<base64 hmac-sha256>

segredo: NECTA_WEBHOOK_SECRET (formato whsec_<base64>)
conteúdo assinado: "{svix-id}.{svix-timestamp}.{corpo bruto}"
tolerância de replay: 300s
A URL https://complyroute.com.br/api/v1/acquirers/necta/webhook precisa ser cadastrada manualmente no painel da Necta (evento por evento, ou "todos") para que os eventos cheguem — isso é um passo operacional, não uma configuração de código.

8.6 Ferramentas de validação

  • tests/unit/test_necta_client.py — 12 testes cobrindo autenticação/cache, reauth em 401, montagem de payload por método, mapeamento de status e verificação de assinatura Svix, usando httpx.MockTransport (sem rede real);
  • tests/integration/test_acquirers.py — testes do endpoint de webhook (assinatura válida, inválida, venda desconhecida);
  • scripts/necta_smoke_test.py — chama o NectaClient direto contra a API real (sandbox/produção conforme .env), fora do resto da aplicação: python scripts/necta_smoke_test.py [--amount N] [--refund UUID].

13. Deploy & Infraestrutura

Hospedado no Render (instância free) sob o domínio complyroute.com.br. Não há render.yaml no repositório — a configuração do serviço é feita diretamente no dashboard da Render.

13.1 Cold start e o workflow de keep-alive

Instâncias free do Render entram em modo de espera após ~15 minutos sem tráfego, e a próxima requisição sofre um "cold start" (tela de "Service waking up" por alguns segundos). Para reduzir a frequência disso, .github/workflows/keep-alive.yml faz um GET /health a cada 10 minutos via GitHub Actions.

Isso é um paliativo, não uma garantia: (1) o GitHub Actions pode atrasar execuções agendadas, especialmente nos primeiros minutos após o workflow ser criado ou em horários de pico; (2) workflows agendados são desativados automaticamente pelo GitHub após 60 dias sem nenhum commit no repositório. A eliminação completa do cold start exige upgrade para uma instância paga do Render.

15. Pendências Conhecidas

Lista honesta do que ainda falta, para orientar o próximo trabalho — nada aqui é urgente por si só, mas cada item foi observado diretamente no código durante esta documentação.

Roteamento

  • As 12 regras são fixas no código; a tabela routing_rules e o endpoint GET /routing/rules não as alimentam de fato — não há hoje como um operador mudar o roteamento sem um deploy.
  • As flags Acquirer.supports_debit/pix/boleto existem no banco mas não são consultadas pelo motor de roteamento.

Autorização

  • Os papéis (admin/financial/technical/readonly) estão no JWT mas nenhum endpoint valida o papel do usuário — qualquer usuário autenticado pode chamar qualquer rota.

Antifraude

  • Os sinais de maior peso (velocidade de IP — 30%, BIN em lista negra — 25%, divergência geográfica — 15%) são placeholders que sempre retornam 0 — o score hoje é, na prática, dominado pelo sinal de valor anômalo (10%) e pela ausência de device fingerprint (20%).

Integração Necta

  • Sem suporte a 3DS para cartão de crédito (a API da Necta oferece o fluxo completo);
  • Sem pré-autorização/captura em dois passos;
  • Cartão trafega como PAN bruto — a Necta também oferece tokenização client-side (networkToken/cardTokenId) que reduziria o escopo PCI;
  • Sem job periódico de conciliação/reconsulta para vendas presas em processing caso a entrega de um webhook falhe — hoje depende inteiramente do webhook chegar;
  • Quando o comprador não informa telefone/endereço completos, o cliente envia dados placeholder em vez de rejeitar a venda — aceitável para teste, questionável para produção.

Webhooks de saída

  • Modelo e assinatura HMAC já existem, mas o disparo assíncrono real (via Celery) ainda é um TODO — hoje nada é efetivamente entregue aos clientes cadastrados.

Chaves de API

  • Modelo APIKey existe e o dashboard tem um painel para isso, mas não há endpoint de API para criar/listar/revogar chaves.

Deploy

  • Sem render.yaml — a configuração do serviço vive só no dashboard da Render, não versionada;
  • O workflow de keep-alive reduz mas não elimina o cold start (ver seção 13.1).
